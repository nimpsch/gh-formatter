# gh-formatter

Python formatter for GitHub Actions workflows/actions. Source in
`src/gh_formatter/`, tests in `tests/`, sample workflows in `examples/`.
All tooling runs through the project venv: `.venv/bin/...`.

## Delegation policy (always orchestrate)

Default to delegating; the main session plans, decides, and reviews — the
roles below do the volume work. Refer to roles only by name; their model
and effort tiers live in `.claude/agents/` and may be retuned without
touching this policy.

- **Explore** — any code-location question ("where is X", "what references
  Y", file-pattern lookups). Never run broad searches in the main session.
- **recon** — before designing a fix or feature, have recon map the
  relevant subsystem and report constraints. Read at most 1–2 files
  directly; beyond that, delegate.
- **mechanic** — once a change is precisely specified: repetitive
  multi-file edits, fixture updates after an order/config change,
  black/ruff autofixes, reformatting the repo's own YAML.
- **gate** — after every code change, run the full quality gate through
  gate instead of invoking the six tools inline.

Keep in the main session: design decisions, edits to
`src/gh_formatter/comments.py` (the regression-prone comment surgery),
API/interface changes, anything the user must decide, and final review of
delegated work.

When a delegated result looks wrong or incomplete, escalate to the main
session rather than re-delegating in a loop.

## Verification

The full gate (what `gate` runs): pytest, ruff, black --check, mypy,
yamllint --strict, `gh-formatter --check . examples/*.yml`. A change is
done only when all six pass and the repo's own YAML stays idempotent.

`config.py`'s DEFAULT_CONFIG is the source of truth for options; keep
`.gh-formatter.yml` and the README config block in sync with it.

## Editor integration (LSP + VSCode)

`src/gh_formatter/lsp/` is a Language Server Protocol frontend
(`gh-formatter-lsp` console script, built on `pygls`) — `core.py` holds
pure, pygls-free helpers (`run_pipeline`, `diagnostic_to_lsp_range`),
`server.py` is the thin `@server.feature` glue. `pygls` is a **core**
dependency (not an extra) so `pip install gh-formatter` gives you
`gh-formatter-lsp` for free — don't move it back behind an optional extra
without a real reason, since that was a deliberate choice to make the
editor experience zero-extra-steps.

`editors/vscode/` is a companion VSCode extension (TypeScript,
`vscode-languageclient`). It's a separate npm project, not part of the
Python gate — verify it with `npm install && npm run compile` inside that
directory. **`compile`/`package` succeeding is not enough to prove the
extension works** — `tsc --noEmit` only checks types, and `vsce package`
doesn't run the packaged code. A real bug (`.vscodeignore` excluding
`node_modules/**` wholesale, silently stripping the real runtime
dependency `vscode-languageclient` out of every built `.vsix`) went
undetected through many rounds of protocol-level server testing because
none of that touched the actual Node.js extension host — it also went
undetected by VSCode itself for a while: once an activation crash occurs
a few times, VSCode can auto-disable the extension entirely, so even a
correctly fixed reinstall silently does nothing until it's manually
re-enabled in the Extensions view. Before declaring a change to
`editors/vscode/` working, load the packaged `out/extension.js` in plain
Node (`node -e "require('./out/extension.js')"` from inside the extracted
VSIX's `extension/` dir) and confirm it fails only on the `vscode` module
itself (expected outside the real host) and nothing else — that catches
missing-dependency bugs `tsc`/`vsce package` don't; if a real user report
says "nothing happens" after confirming the package is correct, also
check whether the extension is disabled (`code --list-extensions`, or
VSCode's own state -- see git history for how to query it directly).
`compile` now runs `tsc --noEmit` (types only) then bundles everything
through `scripts/esbuild.mjs` into a single `out/extension.js` (`external:
['vscode']`, nothing else) — that's what makes excluding
`node_modules/**` in `.vscodeignore` correct again: nothing outside
`vscode` itself needs to resolve at runtime, so the whole "forgot to ship
a runtime dependency" bug class is now structurally impossible rather
than just fixed once. It mirrors Microsoft's own Python tool extensions
(black-formatter, pylint, ...): `gh-formatter.importStrategy` picks
between `useBundled` (default — runs a vendored copy of gh-formatter +
deps shipped inside the extension, via any Python 3 interpreter on PATH,
no pip install needed by the end user) and `fromEnvironment` (use an
already-installed `gh-formatter-lsp`, to match a pinned pre-commit/CI
version). The vendored copy lives at `editors/vscode/bundled/libs/`,
regenerated by `editors/vscode/scripts/vendor_libs.sh` (wired into
`npm run vscode:prepublish`) — it's gitignored like `node_modules`/`out`,
never committed; only `bundled/tool/lsp_server.py` (the bootstrap that
adds `../libs` to `sys.path`) is hand-written source.

`DOCUMENT_SELECTOR` in `extension.ts` deliberately has no `language`
filter, only `scheme`/`pattern` — GitHub's own "GitHub Actions" extension
reassigns workflow files to a separate language id
(`github-actions-workflow`) instead of `yaml`, so filtering on `language`
silently breaks for anyone who has that extension installed. For the same
reason, `activationEvents` lists both `onLanguage:yaml` and
`onLanguage:github-actions-workflow`, and the one-time default-formatter
prompt (`promptDefaultFormatter`) sets `editor.defaultFormatter` for both
language ids, not just `yaml`. Don't reintroduce a `language: 'yaml'`
filter without accounting for this.

Publishing the extension to the VSCode Marketplace (`vsce publish`)
requires the maintainer's own publisher account and personal access
token — never attempt this autonomously; it's a manual step for the user.

`editors/vscode/package.json`'s `version` is kept identical to
`src/gh_formatter/__init__.py`'s `__version__` (the PyPI package version)
automatically — `npm run sync-version` (`scripts/sync_version.mjs`, wired
first in `vscode:prepublish`) copies it over. `__init__.py` is the single
source of truth; don't hand-edit `package.json`'s `version` directly, it
gets overwritten on the next package/publish anyway.
